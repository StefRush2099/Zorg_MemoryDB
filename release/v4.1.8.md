# Zorg MemoryDB v4.1.8

## Summary

- Publishes the live ANN recall repair in the package schema source.
- Uses `embeddinggemma-300m-qat-q8_0` as the canonical packaged ANN recall model.
- Raises HNSW search depth, enables strict iterative scan, and filters
  `capture:%` telemetry before vector ranking.
- Updates stale plugin/MCP version strings and aligns package/gauge metadata at
  `v4.1.8`.

## Upgrade Notes

Use this release as a pinned, whole-package upgrade. Do not mix the `v4.1.8` database SQL, plugin build, LAN Command Chat files, or package metadata with older release files.

### Before upgrade

1. Confirm the target is a separate approved install or local LAN Command Chat update surface; do not use the maintainer source system as an external connector-acceptance target.
2. Record the current package version, enabled memory plugin, OpenClaw version, PostgreSQL version, pgvector version, and LAN Command Chat service state.
3. Back up PostgreSQL before applying packaged SQL. Keep the backup private and prove it is listable before proceeding.
4. Confirm the ANN embedding model route is available for `embeddinggemma-300m-qat-q8_0` and that existing source memory rows are not pruned or rewritten.
5. Preserve current LAN Command Chat `.env.local`, certificates, uploads, logs, and service files; those runtime artifacts are not part of the public package.

### Database component map for LLM upgraders

An LLM performing this upgrade must understand the database as a source-preserving recall system, not as a cache that can be truncated. The packaged SQL under `package/zorg/db` is the contract.

1. Required extensions: `pgcrypto`, `pg_trgm`, and `vector`. The ANN path depends on pgvector HNSW indexes, and text fallback depends on trigram and full-text indexes.
2. Canonical source memory tables: `zorg_logic_rules`, `zorg_memory`, `memory_source_chunks`, and `lan_chat_messages`. These are source records and must not be deleted, collapsed, or rewritten during the upgrade.
3. Rule weighting tables: `zorg_logic_rule_dynamic_weights`, `memory_query_observations`, and `memory_recall_hints` keep recall weights, query aliases, and learned feedback. Preserve them and let idempotent SQL add missing rows or columns.
4. Semantic graph tables: `memory_entities`, `memory_associations`, `memory_semantic_nodes`, and `memory_semantic_edges` hold derived relationship structure. They can be augmented by SQL, but existing active rows are part of recall context.
5. Typed operational event tables: `memory_model_outputs`, `memory_tool_calls`, `memory_tool_results`, `memory_code_operations`, `memory_decisions`, `memory_errors`, `memory_corrections`, `memory_external_actions`, `memory_verifications`, and `memory_event_links` keep additive execution history. The upgrade wires these into semantic capture with triggers; it must not prune the source events.
6. ANN tables: `memory_embedding_model_slots` declares provider/model slots, `memory_ann_model_embeddings` stores source embeddings, `memory_query_embedding_cache` stores query embeddings, and `memory_ann_occurrence_groups` groups exact-repeat derived vectors. In `v4.1.8`, the packaged default is provider `local`, model `embeddinggemma-300m-qat-q8_0`, dimension `768`.
7. Queue tables: `memory_semantic_work_queue` is the additive embedding/semantic queue. `memory_ann_enqueue_source_v1`, `memory_enqueue_semantic_job`, and `memory_ann_enqueue_due_sources_v1` coalesce derived work by source identity. Queue rows may be retried or requeued; source memory rows must remain intact.
8. Recall materialized views: `zorg_memory_search_fast_mv` and `zorg_master_context_mv` provide bounded text recall and master context. Refresh them after schema/data changes with `refresh_zorg_memory_search_fast_mv()` and `refresh_zorg_master_context()` when those functions exist.
9. Recall functions: `memory_recall_v2` is the canonical hybrid API. It combines exact aliases, mandatory logic-rule preflight, bounded materialized-view recall, optional deep weighted recall, and pgvector ANN recall. `memory_ann_recall` and `memory_provider_ann_recall` are low-level ANN providers and are not a substitute for current-turn preflight.
10. Core preflight: `zorg_core_rule_preflight_v1` and `zorg_get_logic_context` keep high-priority operating rules at the front of recall. Verify current-turn recall through the application/tool preflight path, not only by calling pgvector directly.
11. Capture triggers: `memory_queue_semantic_capture_v1` and triggers named `zorg_semantic_capture_*` enqueue derived work from typed event tables. `memory_semantic_capture_trigger_status_v1` reports whether each expected trigger exists.
12. DB-owned scheduler: `memory_db_scheduled_jobs`, `memory_db_scheduled_job_runs`, `memory_db_claim_due_jobs`, `memory_db_run_due_jobs_sql`, `memory_db_semantic_worker_batch_sql`, and `memory_db_health_check_sql` keep database-owned maintenance jobs. External cron-style LLM jobs must not be recreated as command-executing rows.
13. LLM job queue compatibility: `memory_llm_scheduled_jobs`, `memory_llm_job_queue`, `memory_llm_enqueue_due_jobs_v1`, and `memory_llm_next_due_v1` remain generic queue surfaces. The v4.1.8 SQL removes forbidden historical ANN command jobs named `zorg-memory-ann-prefill` and `zorg-memory-ann-maintenance`.
14. Worker script: `package/zorg/memory/memory_embedding_worker.py` claims `memory_semantic_work_queue` rows and writes real model vectors into `memory_ann_model_embeddings`. Configure it with `SQL_MEMORY_MAP`, `ZORG_EMBEDDING_PROVIDER=local`, `ZORG_EMBEDDING_MODEL=embeddinggemma-300m-qat-q8_0`, and the local Ollama-compatible endpoint before expecting ANN queue depth to drain.

### Database and plugin upgrade

1. Install or stage the pinned package from the `v4.1.8` tag or release archive.
2. Apply the package SQL through the reviewed installer path so SQL errors stop the upgrade instead of being ignored. The SQL files are idempotent; rerunning them should add missing compatible objects without removing source rows.
3. Apply the base schema first, then compatibility and recall SQL, then ANN/default-provider SQL, then typed-event/capture/scheduler SQL. A clean install or upgrade must include `schema.sql`, `memory_runtime_compat_2026_07_21.sql`, `memory_recall_fast_mv_bounded_2026_07_10.sql`, `memory_recall_v2_bounded_2026_07_10.sql`, `memory_ann_bootstrap_2026_07_12.sql`, `memory_ann_provider_defaults_2026_07_12.sql`, `memory_typed_events_2026_07_16.sql`, `memory_semantic_capture_triggers_2026_07_17.sql`, and `memory_core_scheduler_2026_08_06.sql`.
4. Verify `memory_ann_recall()` and `memory_recall_v2` use the packaged `embeddinggemma-300m-qat-q8_0` defaults, higher HNSW search settings, strict iterative scan, and `capture:%` telemetry filtering.
5. Start or run the embedding worker after SQL is applied. It should turn queued `zorg_memory`, `logic_rule`, and `source_chunk` rows into active `memory_ann_model_embeddings` rows using 768-dimensional real model vectors.
6. Rebuild and inspect the `zorg-memorydb` plugin runtime, not only the manifest. Confirm the MCP/server version reports `4.1.8`.
7. Restart only the affected Gateway/plugin runtime after the package has been staged and configuration has been preserved.

### Database verification queries

Run these checks after SQL and worker startup. Replace connection flags with the target's private PostgreSQL configuration; do not put credentials in docs or chat.

```sql
select extname from pg_extension where extname in ('pgcrypto','pg_trgm','vector') order by extname;
select slot_key, embedding_provider, embedding_model, embedding_dim, enabled, is_default from memory_embedding_model_slots order by slot_key;
select count(*) filter (where active) as active_embeddings,
       count(*) filter (where active and embedding_provider='local' and embedding_model='embeddinggemma-300m-qat-q8_0') as active_default_embeddings,
       count(*) filter (where active and vector_norm(embedding)=0) as zero_norm_vectors
from memory_ann_model_embeddings;
select status, count(*) from memory_semantic_work_queue group by status order by status;
select indexname from pg_indexes where tablename='memory_ann_model_embeddings' and indexdef ilike '%hnsw%' order by indexname;
select * from memory_ann_bootstrap_status_v1;
select * from memory_semantic_capture_trigger_status_v1 order by table_name;
select memory_query_embedding_cache_exists_v1('current-turn recall verification');
select source_type, recall_mode, rank, score_reason
from memory_recall_v2('current-turn recall verification', 5, '{"mode":"deep"}'::jsonb);
```

Healthy results for v4.1.8 are: extension rows present, one enabled default slot for `embeddinggemma-300m-qat-q8_0`, no failed queue rows, no zero-norm active vectors, HNSW indexes present, `forbidden_ann_job_rows = 0`, capture triggers enabled for every existing typed-event table, and `memory_recall_v2` returning hybrid recall rows through the stored procedure path.

### LAN HTTPS and self-signed certificate setup

The release package preserves certificates but does not ship private keys. If a target has no approved LAN certificate yet, create one on the target host before enabling HTTPS. Use the target's real LAN IP or DNS name; do not copy the maintainer host's certificate to another machine.

1. Choose the HTTPS names first. For the verified maintainer LAN shape these are `10.6.69.108`, `zorg.hyperdine.local`, `localhost`, and `127.0.0.1`; another host must substitute its own LAN IP and DNS names.
2. Create a private certificate directory owned by the service operator and readable by nginx, then generate a self-signed certificate with SAN entries for every browser-visible address. Example for the maintainer LAN shape:

```bash
install -d -m 700 nginx/certs
openssl req -x509 -newkey rsa:4096 -sha256 -days 825 -nodes \
  -keyout nginx/certs/10.6.69.108.key \
  -out nginx/certs/10.6.69.108.crt \
  -subj "/CN=10.6.69.108" \
  -addext "subjectAltName=IP:10.6.69.108,DNS:zorg.hyperdine.local,DNS:localhost,IP:127.0.0.1"
chmod 600 nginx/certs/10.6.69.108.key
chmod 644 nginx/certs/10.6.69.108.crt
```

3. Make the files available at the paths nginx will read, for example `/etc/nginx/certs/10.6.69.108.crt` and `/etc/nginx/certs/10.6.69.108.key`, without committing them to Git or the release archive.
4. Configure nginx with an HTTP redirect and TLS server blocks. The verified maintainer shape is: port `80` redirects to `https://$host$request_uri`; port `443 ssl` proxies LAN Command Chat to `http://127.0.0.1:3001`; port `8097 ssl` proxies Neural Recall Activity to `http://127.0.0.1:8098`; both TLS blocks use the same certificate/key and set `X-Forwarded-Proto $scheme`.
5. Validate config before reload: `nginx -t` must pass. Then reload or restart nginx through the host-approved service manager.
6. Verify certificate metadata before browser testing:

```bash
openssl x509 -in nginx/certs/10.6.69.108.crt -noout -subject -issuer -dates -ext subjectAltName
```

7. Verify the LAN HTTPS routes with certificate checking disabled only for the self-signed test:

```bash
curl -k -fsS -o /dev/null -w '%{http_code} %{ssl_verify_result} %{url_effective}\n' https://127.0.0.1/
curl -k -fsS -o /dev/null -w '%{http_code} %{ssl_verify_result} %{url_effective}\n' https://127.0.0.1:8097/api/health
```

Healthy results are HTTP `200` from both HTTPS routes. A self-signed certificate normally reports a non-zero curl verify result until the operator installs the cert authority or certificate into the client trust store. The browser will warn on first use unless the client trusts that certificate.

8. Re-run the authenticated browser checks after the TLS change. For LAN Command Chat, confirm `/chat` still renders the `v4.1.8` gauge. For Neural Recall Activity, confirm `https://<lan-host>:8097/` loads and `/api/health` succeeds.
