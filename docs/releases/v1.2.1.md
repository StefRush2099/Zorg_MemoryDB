# Zorg MemoryDB v1.2.1

Released: 2026-05-07

## Summary

This documentation release adds the recommended baseline architecture for making OpenClaw + Zorg MemoryDB practically useful as a personal executive-assistant system, not just a local memory-enabled agent.

## Added

- New guide: [`docs/base-setup.md`](../base-setup.md).
- Recommended instant messaging channel for fast operator control, such as Telegram, WhatsApp, Signal, Discord, Slack, or another preferred direct-message surface.
- Recommended dedicated assistant email account as the public-facing executive-assistant identity so routine communication is filtered through the AI agent instead of the operator's private address.
- Guidance that direct personal-email access is optional and should be governed separately for triage/search/drafting rather than treated as the public address.
- Private GitHub/off-host PostgreSQL backup recommendation for durable MemoryDB recovery.
- Cloudflare Tunnel connector guidance for operator-approved remote URLs and web publishing surfaces.
- Docker + Dockge visibility recommendation so less technical users can see, stop, start, and update the assistant's supporting services from a web UI.

## Public/private boundary

This release includes only public-safe architecture and setup guidance. It does not include private DB dumps, credentials, account tokens, contacts, transcripts, private operator context, or live environment details.

## Verification

- Markdown documentation updated and inspected.
- README, quickstart, Dockge, and positioning docs now link to the baseline setup guide.
- No private secrets or environment-specific values were added.

## Absolute Priority 0: Exhaustive Memory Before Response

The operator does not ask for work in context unless the needed information, access path, rule, contact, precedent, or working solution likely already exists somewhere in durable memory, project history, live configuration, runbooks, prompts, cron jobs, or related system state. A fast or shallow miss is never evidence of absence.

Before replying, asking a question, claiming uncertainty, or reporting a blocker, the assistant must scour the backend memory system deeply and creatively: use broader queries, alternate names, relationship terms, adjacent projects, prior similar tasks, contact records, operational history, runbooks, cron payloads, and live configuration clues until the relevant context is found or genuinely exhausted. Immediate answers are disallowed when memory could contain the answer.

If deep scouring finds information that the first query missed, treat that as a recall-structure failure and immediately add additive retrieval support: aliases, recall hints, semantic/relationship edges, query observations, indexes, materialized/search support, or rule surfaces so the same phrasing is fast and reliable next time. Preserve all source data; improve recall additively only.

Failure reports must not excuse the miss as “not enough information” when the information existed in memory. The correct diagnosis is inadequate recall behavior or structure, and the corrective action is deeper recall plus indexing/hinting/relationship repair.
