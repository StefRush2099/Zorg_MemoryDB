# Zorg MemoryDB v1.2.6

## Summary

This release hardens the public-safe operating model for dynamic, LLM-governed agents. It documents that assistant policy should live in natural-language rules, prompts, runbooks, and DB-backed memory that a live model applies at runtime — not in hidden Python or JavaScript policy scripts.

## Added

- Core no-scripted-policy rule for internal assistant routines.
- LLM-governed email-check pattern: a trigger may detect unread email, but triage, replies, CC/BCC, contact updates, deletion, loop suppression, and escalation are model decisions made from current rules and memory.
- Duplicate-meeting prevention rule for calendar and meeting-related email handling.
- Exact Hyperdine/X article-link rule requiring the verified full per-article anchor URL in paired X teasers.
- Public-safe guidance that Hyperdine/news-feed publishing is an LLM-governed publishing task, with scripts limited to mechanical I/O/API helper roles.

## Changed

- Expanded executive-assistant operating rules to describe dynamic LLM judgment boundaries.
- Expanded templates so new installs inherit the same no-scripted-policy and scheduling safeguards.
- Clarified that when a post is too long, prose or hashtags should be shortened before the verified article URL is shortened or removed.

## Verification

- Markdown docs and templates updated.
- Shell scripts passed `bash -n` validation.
- Python helper files passed `py_compile` validation.
- Docker Compose configuration validated locally.

## Privacy

This release publishes only public-safe structure, templates, and operating rules. It does not include private memory rows, database dumps, contacts, emails, transcripts, credentials, live account data, internal hosts, or operator context.

## Absolute Priority 0: Exhaustive Memory Before Response

The operator does not ask for work in context unless the needed information, access path, rule, contact, precedent, or working solution likely already exists somewhere in durable memory, project history, live configuration, runbooks, prompts, cron jobs, or related system state. A fast or shallow miss is never evidence of absence.

Before replying, asking a question, claiming uncertainty, or reporting a blocker, the assistant must scour the backend memory system deeply and creatively: use broader queries, alternate names, relationship terms, adjacent projects, prior similar tasks, contact records, operational history, runbooks, cron payloads, and live configuration clues until the relevant context is found or genuinely exhausted. Immediate answers are disallowed when memory could contain the answer.

If deep scouring finds information that the first query missed, treat that as a recall-structure failure and immediately add additive retrieval support: aliases, recall hints, semantic/relationship edges, query observations, indexes, materialized/search support, or rule surfaces so the same phrasing is fast and reliable next time. Preserve all source data; improve recall additively only.

Failure reports must not excuse the miss as “not enough information” when the information existed in memory. The correct diagnosis is inadequate recall behavior or structure, and the corrective action is deeper recall plus indexing/hinting/relationship repair.
